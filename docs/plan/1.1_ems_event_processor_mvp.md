## 1. Problem Statement

EMS receives event information in an Excel workbook formatted for human reading rather than data processing. Event information is spread across repeated blocks, page headers, notes, contacts, and equipment-request lines. Staff need a simple way to select the source workbook and produce a more organized workbook that is easier for humans to review and can later support automated work-order generation.

The MVP will provide a standalone Windows desktop application named **EMS Event Processor**. It will transform one selected Excel file into one cleaned Excel workbook and, when necessary, a separate issues workbook.

## 2. Goals

- Provide one simple desktop screen for selecting an Excel file.
- Convert the report-style event workbook into organized event and equipment data.
- Preserve the source workbook as the ultimate source of truth.
- Keep equipment requests as separate records while also providing equipment totals.
- Ask the user where to save the generated workbook.
- Record ambiguous or unprocessed information in a separate issues workbook.
- Create a clean data foundation for future work-order generation.

## 3. Non-Goals

- Date filtering or date-range selection.
- Work-order creation or assignment.
- Uploading to the school's work-order website.
- Connecting to SharePoint, Microsoft Graph, or Power BI.
- User accounts, authentication, or cloud storage.
- Automatic modification of the original input workbook.
- Inventing setup, takedown, staffing, or equipment information.
- A full inventory-management system.
- Advanced configuration screens or user-editable mapping tables.
- AI or machine-learning interpretation.

## 4. Personas & User Stories

- **As an EMS staff member**, I want to select an event Excel file so that I can process it without manually editing the report.
- **As an EMS staff member**, I want to choose where the output is saved so that I can place it in the correct working folder.
- **As an EMS staff member**, I want events and equipment requests separated into readable tables so that I can review the information quickly.
- **As an EMS staff member**, I want unclear records listed in an issues workbook so that I know what requires manual review.
- **As a future developer**, I want stable event and equipment identifiers so that later work-order automation can use the cleaned output.

## 5. Functional Requirements

- **FR-1.** The application MUST open as a simple single-screen desktop application.
- **FR-2.** The application MUST allow the user to choose a local .xls or .xlsx file.
- **FR-3.** The application MUST display the selected filename before processing.
- **FR-4.** The application MUST allow the user to choose the output location and filename.
- **FR-5.** The application MUST preserve the original input file and MUST NOT modify it.
- **FR-6.** The application MUST identify event blocks, including blocks separated by blank rows or report page breaks.
- **FR-7.** The application MUST create an Events table with one row per event occurrence.
- **FR-8.** Events SHOULD include event date, reservation and event times, location, event name, setup/event type, group, status, contacts, reservation identifiers, and notes when present.
- **FR-9.** The application MUST create an Equipment Requests table with separate rows for separate equipment requests.
- **FR-10.** Each equipment request MUST retain its related event identifier.
- **FR-11.** The application SHOULD separate an equipment quantity from its description when the source clearly provides both.
- **FR-12.** The application MUST preserve original equipment-request text when parsing or normalization is uncertain.
- **FR-13.** The application MUST create an Equipment Summary table that totals clearly parsed quantities by equipment description.
- **FR-14.** The application MUST preserve recurring event occurrences as separate event records and SHOULD add a recurrence relationship when supported by the source.
- **FR-15.** The application MUST create an issues workbook when ambiguous, incomplete, or unparsed information is encountered.
- **FR-16.** The issues workbook MUST identify the issue, preserve relevant original text, and include source location information when available.
- **FR-17.** The application MUST show processing progress or status.
- **FR-18.** The application MUST show a completion summary containing output paths and counts of events, equipment requests, and issues.
- **FR-19.** The application MUST show a clear error if the file cannot be read or the output cannot be saved.
- **FR-20.** The processor MUST use source values as the ultimate source of truth and MUST NOT infer operational requirements absent from the workbook.

## 6. Non-Functional Requirements

- **Performance** — The application SHOULD process the provided 135-page sample workbook in a reasonable desktop time while keeping the interface responsive.
- **Security** — The MVP MUST process local files only and MUST NOT require credentials or transmit workbook contents.
- **Privacy & Compliance** — Logs SHOULD avoid unnecessary personal information. Generated workbooks may contain contact information because it is part of the source data.
- **Accessibility** — The UI SHOULD support keyboard navigation, readable labels, clear errors, and status messages that do not rely only on color.
- **Reliability** — A problem in one record MUST NOT stop all valid records from being exported. The problem MUST be recorded in the issues workbook.
- **Observability** — The application SHOULD record a concise local log containing input filename, output filename, timestamp, counts, and error summaries.
- **Maintainability** — Parsing, normalization, workbook export, and UI code SHOULD be separate testable modules.
- **Backward compatibility** — The original source file MUST remain unchanged.

## 7. Acceptance Criteria

- **AC-1.** Given a readable .xls or .xlsx workbook, when the user selects it and chooses an output location, then the application creates the cleaned workbook there.
- **AC-2.** Given the Setup Worksheet format, when processing completes, then the output contains organized event records rather than report headers, page numbers, and repeated layout rows.
- **AC-3.** Given one event with multiple equipment requests, when processing completes, then the event appears once in Events and each request appears as its own Equipment Requests row.
- **AC-4.** Given clearly parsed equipment quantities, when processing completes, then Equipment Summary contains correct totals.
- **AC-5.** Given an ambiguous value, when processing completes, then the original text is preserved and the problem appears in the issues workbook.
- **AC-6.** Given recurring events on multiple dates, when processing completes, then each occurrence remains a separate event record.
- **AC-7.** Given a problem affecting one record, when processing completes, then valid records are exported and the problem is documented.
- **AC-8.** Given an unreadable file or invalid output location, when processing is attempted, then the application displays an error and does not claim success.
- **AC-9.** Given any input workbook, when processing completes, then the original workbook has not been modified.

## 9. API Surface

There is no external API in the MVP.

The internal processing engine SHOULD expose a callable function similar to:

    process_workbook(input_path, output_path) -> ProcessingResult

ProcessingResult should include:

- output workbook path
- issues workbook path, if created
- event count
- equipment-request count
- summary-row count
- issue count
- warnings
- fatal errors

The internal function SHOULD be usable independently of the Tkinter interface so later work-order generation can reuse it.

## 10. UI / UX

The MVP should use one simple screen.

### User flow

1. Open EMS Event Processor.
2. Click Choose Excel File.
3. Select a local .xls or .xlsx file.
4. Review the selected filename.
5. Click Process File.
6. Choose the output filename and location using a save dialog.
7. Wait for processing to finish.
8. View the completion summary.
9. Optionally open the output folder.

### UI controls

- Application title: EMS Event Processor
- Choose Excel File button
- Selected-file display
- Process File button
- Progress/status message
- Output-location prompt
- Completion summary
- Open Output Folder button, if practical

The MVP does not need multiple pages, settings, login, date controls, preview screens, or advanced configuration.

## 11. AI / ML Considerations

Not applicable. The MVP should use deterministic parsing and explicit rules. Ambiguous information should be recorded for review rather than interpreted by an AI model.

## 12. Integration Points

### MVP integrations

- Local filesystem

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Source report layout changes | H | H | Detect labels and event patterns rather than relying only on fixed row numbers. |
| Equipment descriptions are inconsistent | H | M | Preserve original text and use conservative normalization. |
| Operational information is mixed into notes | H | M | Preserve notes and flag information that cannot be classified confidently. |
| A malformed record stops processing | M | H | Process records independently and write failures to the issues workbook. |
| Future website requires another structure | H | H | Keep website integration out of the MVP and preserve stable source identifiers. |
| .xls and .xlsx behave differently | M | M | Test both formats using representative fixtures. |

## 15. Rollout Plan

- No feature flag is required for the standalone MVP.
- Build and test locally using sanitized or approved sample workbooks.
- Validate output with EMS staff before treating transformation rules as final.
- Package a Windows executable after the local version works.
- Pilot with a small number of real files.
- Keep the original workbook as the recovery source.
- Roll back by using the original workbook and a previous application build.

## 16. Test Plan

- **Unit** — Test event-block detection, date/time parsing, contact parsing, quantity parsing, equipment-row creation, recurring-event handling, issue creation, and summary totals.
- **Integration** — Process representative .xls and .xlsx files and verify the generated workbooks.
- **End-to-end** — Select a file through the UI, choose an output location, process it, and verify that the output files open successfully.
- **Error cases** — Test missing files, unreadable files, unsupported extensions, empty workbooks, malformed rows, missing identifiers, ambiguous quantities, and invalid save locations.
- **Data preservation** — Verify that the original input file remains unchanged.
- **Manual exploratory** — Review event grouping, equipment rows, recurring events, notes, contacts, formatting, filters, frozen headers, column widths, and issues output using the provided sample.
